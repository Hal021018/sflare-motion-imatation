# 接入方案：游戏调用固定动作服务

> **历史文档（2026-10-19）**：最初的设计方案。当前接口与流程见 [HANDOVER](../HANDOVER.md)。

> 目标：把 `sflare_game_ros` 的 `moveaction` 从"自己连控制器 + 5 个硬编码点位"改成"给动作服务下发动作名 + 取标准姿态"。
> 依据：`00-关键事实.md`。动作服务为黑盒，不改其代码。

## 1. 现状 vs 目标

| 环节 | 现状 | 目标 |
|---|---|---|
| 选动作 | `MOVE_ACTION_POSITIONS` 硬编码 5 组 9 轴点位 | 动作服务 19 个命名动作 |
| 运动 | 游戏进程内 `PallasGameController.movej()` | 发布 `std_msgs/String` 到 `/dual_arm_xcdl_action` |
| 保持 | `sleep(move_hold_sec)` 后读标准 | 服务内部 `wait` 展示窗口 |
| 回零 | 游戏自己 `move_j(全零)` | 动作编排自带回零 |
| 完成信号 | `movej()` 返回 | 状态话题 `busy → ready` |
| 急停/限位 | 游戏 `self_check` 读控制器 | 动作服务内部处理 + `/e_stop` |
| 评分 | `/arm_joint_states` + 权重表 | **不变** |

## 2. 接口契约（沿用现有 `.srv`，不破坏上位机）

`GameCommand.request_type` 仍是 `string`，扩展语法：

| 请求 | 行为 |
|---|---|
| `moveaction` | 从配置的候选动作里随机选一个（保持现有玩法） |
| `moveaction:like` | 指定动作名，`:` 后为动作名 |
| `calculate_score` | 不变 |
| `stop` | 改为向动作服务发 `stop` 字符串 |
| `self_check` | **保留，且仍作为 moveaction 的前置门禁**；但先读状态话题，非 `ready` 直接返回 `ROBOT_BUSY`，不做连接尝试 |
| `release_limit` | 建议删除，返回 `UNKNOWN_REQUEST`；理由见 §8.2（不是抢连接，而是两套脱限实现） |

`moveaction` 的 `data` 增加：`action_name`、`action_index`（候选表序号）、`service_status`、`standard_source`（`json` / `joint_states`）。

## 3. 新流程

```
moveaction
  ├─ 读状态话题，必须为 ready；否则 ROBOT_BUSY / EMERGENCY_STOP / OVERTRAVEL
  ├─ self_check（只读，执行前状态仍为 ready 时才连控制器）
  ├─ 选动作名（候选表随机 / 请求指定）
  ├─ 清空本轮标准（generation+1）
  ├─ 发布动作名
  ├─ 等状态离开 ready（busy），最多 N 秒 → 否则 ACTION_NOT_STARTED
  ├─ 等状态回到 ready，上限按动作时长表配置 → 否则 ACTION_TIMEOUT
  ├─ 期间若进入 physical_alarm / recover_required / failed / fatal_network → 对应错误码
  └─ 读标准姿态（见 §4），写入 reference，返回 OK
```

`stop`：发 `"stop"`，立刻返回 `OK`；同时 `_clear_reference()`。

## 4. 标准姿态来源

**阶段一（本次实现）：JSON 指令角。**
从动作服务的 `actions/*.json` 读 `keyframes[0]` 的右臂 7 轴（度），作为标准。

- 优点：确定、可复现、零延迟、不依赖反馈时序
- 缺点：是指令值，真机稳态可能差 1–3°（评分有 ±5° 容差，可接受）
- 落地：动作表内置到 `config/actions.yaml`（动作名 → 7 轴角度 + 预计时长），避免运行时读机器人文件

**阶段二（后续可选）：展示窗口实测。**
订阅 `/arm_joint_states`，检测"连续 N 帧变化 < 阈值"且"接近 JSON 指令角"，抓实测值替换。需要先确认 `/arm_joint_states` 的真实发布频率与稳定性。

## 5. 服务状态 → 游戏错误码

| 服务状态 | 游戏 `code` |
|---|---|
| `ready`（请求前） | 继续 |
| `busy`（请求前） | `ROBOT_BUSY` |
| `physical_alarm` | `EMERGENCY_STOP` |
| `recover_required` | `EMERGENCY_STOP` |
| `power_not_ready` | `POWER_NOT_READY`（新增） |
| `connection_failed` / `handle_busy` | `SERVICE_UNAVAILABLE`（新增） |
| `limit_recovery_failed` | `OVERTRAVEL` |
| `invalid_target` / `unknown_command` / `single_not_support` | `ACTION_REJECTED`（新增） |
| `fatal_network` / `failed` | `ACTION_FAILED`（新增） |
| 超时未开始 | `ACTION_NOT_STARTED`（新增） |
| 超时未结束 | `ACTION_TIMEOUT`（新增） |

## 8. 风险与前置

### 8.1 连接共存：只在动作执行期间冲突

动作服务的连接是**按动作临时建立**的：`play()` 开始时 connect，结束时 `safe_cleanup_arm` + disconnect。空闲时不持有控制器连接。

真机已验证：旧生产服务运行中，游戏 `self_check` 仍能正常 connect/read/disconnect 并返回 `OK`。

因此：

| 场景 | 是否会冲突 |
|---|---|
| 服务空闲 + 游戏 `self_check` | 不会（已实测） |
| 服务执行动作中 + 游戏 `self_check` | **会**，connect 拿到 `busy` 类错误 |
| 服务执行动作中 + 游戏 `moveaction` | 不会连控制器（只发话题），但会收到 `busy` 状态 |

对策：

- `self_check` 先读状态话题，非 `ready` 直接返回 `ROBOT_BUSY`，不发起连接；
- 连接失败若为 `-20035/-20039`，映射为 `SERVICE_UNAVAILABLE` 并提示"动作服务正在执行"，而不是笼统的 `OPERATION_FAILED`；
- 新 `moveaction` 本身不再直接连控制器（除了一次前置 `self_check`），把冲突窗口压到最小。

### 8.2 `release_limit` 建议删除

不是因为抢连接，而是：

- 服务的 `limit_recovery` 是**内置自动脱限**（有报警码 + 真实限位证据门禁、90s/600 脉冲上限）；
- 游戏侧的 `release_limit` 是另一套 Jog 实现（`margin=2°`、`max_cycles=25`），参数与门禁都不同；
- 两套实现同时存在，现场无法判断该信哪个，且游戏侧 Jog 会绕过服务的恢复门禁。

若现场确实需要手动脱限，应由动作服务侧提供命令，而不是游戏自己 Jog。

### 8.3 其它

1. **动作时长未知**：`dance` 等可能几十秒。`action_timeout_sec` 按动作表配置，默认 60s。
2. **`/e_stop` 有发布者但无数据**：不能用于门禁，急停判断依赖动作服务状态。
3. **接口兼容**：`moveaction:xxx` 语法对现有上位机透明（旧的 `moveaction` 仍可用）。
4. **所有权**：动作服务与游戏不能同时执行运动；游戏改为话题调用后不再有第二个运动发起者。
